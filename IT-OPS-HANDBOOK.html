PART 1

What this toolkit is

orientation

The bims-corp-ops repo is a toolkit for the engineering operations work BIMS-Corp does every day — bug intake, ticket writing, codebase questions, PR review against acceptance criteria. It uses Claude Code as the execution layer; you don't have to "know AI" to use it. You describe what you want in plain English, the toolkit handles the lookups and produces the artifact (a Jira-ready ticket, a cited answer, a PR verdict).

The point is to make your job faster:

  • Better tickets to the subcontractor team, faster. With file:line evidence and acceptance criteria they can actually act on — fewer round-trips per bug.
  • Codebase questions answered with citations, not guesses. "Where is property creation handled" gets you an exact file and line range, not a 30-minute grep session.
  • PR reviews with per-criterion verdicts, not vibes. Each acceptance criterion gets a PASS / FAIL / NEEDS_INFO with the evidence cited.
  • A single audit trail for everything. Every finding, decision, and review is recorded with attribution — you can prove what was filed when, by whom.

This toolkit is for ops work, not code-writing. You're not being asked to write code, and you don't need to. You're being given faster tools to do the work you already do.
PART 2

One-time setup

~10 min · once per machine

Install once per Mac. After that, everything in this handbook works. Every command runs in Terminal (⌘ Space → type Terminal).

1

Install the Homebrew packages

One command installs the CLI tools the toolkit needs:

RUN IN TERMINAL
$ brew install gh jq sqlite3 ast-grep gitleaks
✓
You should see each package downloading + installing. Takes 1-3 minutes.

Install Homebrew first:

RUN IN TERMINAL
$ /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

Follow the prompts (it'll ask for your Mac password and confirm before each step). When it finishes, re-run the package install command above.

2

Install uv + graphify (Python tooling)

uv is the Python package manager the workbench uses. graphify is the code-indexer that powers /bims-ask.

RUN IN TERMINAL
$ curl -LsSf https://astral.sh/uv/install.sh | sh
RUN IN TERMINAL
$ source ~/.zshrc 2>/dev/null || true
$ uv tool install graphifyy
✓
Verify with uv --version + graphify --version. Both should print version strings.
3

Install Claude Code

Claude Code is the execution layer — the CLI you'll be talking to.

RUN IN TERMINAL
$ brew install claude-code
✓
Verify with claude --version — should print Claude Code 1.x.x.
4

Clone the workbench

This pulls down the toolkit itself. gh repo clone uses your GitHub credentials automatically (you'll be prompted to authenticate the first time).

RUN IN TERMINAL
$ mkdir -p ~/Developer
$ cd ~/Developer
$ gh repo clone bims-corp-ai/bims-corp-ops
$ cd bims-corp-ops

Your GitHub account isn't in the bims-corp-ai org with access to this repo. Ping Greg with your GitHub username; he'll add you. Then re-run the clone.

5

Run setup (twice — first run stops to ask you to configure)

RUN IN TERMINAL (FROM bims-corp-ops/)
$ ./bin/setup --mode secondary

The first run stops partway and tells you to edit state/local-config.json. Open that file in TextEdit:

RUN IN TERMINAL
$ open -e state/local-config.json

Fill in:

  • machine_id — e.g. "alex-ops-laptop"
  • operator — your email
  • BIMS_OPS_ROOT — full path to this repo (run pwd in another Terminal window from this dir to get it)
  • BIMS_LEGACY_ROOT — full path to where the 8 legacy repos live (e.g. /Users/<you>/Developer/BIMS-Corp-LEGACY)

Save the file (⌘ S), then re-run setup:

RUN IN TERMINAL
$ ./bin/setup --mode secondary
✓
Setup runs all the way through this time (~8 minutes). You'll see Summary: 32 pass / 0 warn / 0 fail. If anything fails, the doctor names the exact next command — see Troubleshooting.

The pre-commit safety gate is in the repo but isn't activated locally on old clones. Activate it once:

RUN IN TERMINAL
$ git config --local core.hooksPath .githooks

This blocks commits that accidentally contain API keys or passwords. The workbench remote is public; the gate exists so a mistake doesn't end up on GitHub.

Your first 5 minutes

5 min

Verify the toolkit actually works by running it against a real codebase question. If this works, everything else in the handbook works.

1

Open a Claude Code session

From inside the bims-corp-ops directory:

RUN IN TERMINAL
$ cd ~/Developer/bims-corp-ops
$ claude
✓
Claude loads the workbench's skills and shows its input prompt at the bottom of the Terminal.
2

Always start with please orient

This loads project context — current findings, recent decisions, the list of repos in scope, the operating constraints. Skip it and you'll get worse answers on everything that follows.

TYPE INSIDE CLAUDE
> please orient
✓
Claude prints a 3-second summary: open findings count by severity, recent decisions, sync status, and operating "traps" to be aware of.
3

Try a real query

TYPE INSIDE CLAUDE
> ask: where is the user login controller in PropertyOrganizer-Web
✓
Something like:
RESPONSE
The login controller is at:
  application/modules/users/controllers/users.php:82  (function login())

It validates email_w + password_w, calls users_model->check_front_login,
and redirects to /dashboard on success. The role allowlist is roles 2, 3, 12
(users_model.php:347).

That's the loop: ask in plain English, get an answer with file:line citations, click through to the source if you want to verify. Five seconds vs. thirty minutes of greping.

PART 4

Filing a bug you found

~5 min per bug

When you'd use this: you spotted a bug during PR review, while testing the staging app, or while reading an error log. You want to record it before you forget, so it shows up in the queue for whoever drafts the ticket to the subcontractor team.

1

Record the finding

In Claude Code:

TYPE INSIDE CLAUDE
> record a finding: while reviewing PR #42, I noticed
   that the login form accepts an empty email field and
   returns a 500.

   Reproduce: POST /users/login with email_w='' and
   password_w='anything'. Expected: 200 with validation
   error. Got: 500 with stack trace.
✓
Claude asks for severity (see Part 8), then writes the finding to bims-store. You get back an ID like BIMS-F-2026-05-19-c9e21a60 (severity P1, status open). That ID is the finding's permanent reference — use it any time you mention the bug.
2

What good findings look like

FieldGoodBad
title "Login form 500s on empty email instead of validating" "Login broken"
summary "POST /users/login with email_w='' returns HTTP 500. Form should validate to 200 with error." "Found a bug while reviewing the PR"
reproduction Exact steps: URL, payload, expected vs. actual. Include user ID + role if relevant. "It crashed when I tried it"
file:line If you can find the offending code, cite it: users_model.php:347 Skipping this — fine if you genuinely don't know, but always try.
i
If you don't know severity, leave it at P2 by default. P0 is for production-down or active security issues. P3 is for cosmetic / nice-to-have. See the severity guide in Part 8 if you're not sure.
3

What happens next

The finding sits in bims-store.findings with status open. Someone (you or another ops engineer) picks it up and drafts a ticket (Part 5). When the ticket gets posted to Jira, the finding's status flips to promoted. When the subcontractor team fixes it, the finding moves to resolved.

You can list open findings at any time:

TYPE INSIDE CLAUDE
> list open findings
Part 4 complete
Bugs land in the queue with a permanent ID — no more forgotten observations.
Part 5: Write a ticket →
PART 5

Writing a ticket to India

~10 min per ticket

When you'd use this: a finding is recorded and you need to turn it into a Jira ticket that the subcontractor team can actually act on. The bad version of this task is the tickets you've been writing — loose prose, no repro steps, no file:line evidence, no acceptance criteria. India sends them back asking for more info. Three round-trips later the bug is still there. This workflow eliminates that.

1

Draft the ticket

Once you have a finding ID:

TYPE INSIDE CLAUDE
> /bims-ticket BIMS-F-2026-05-19-c9e21a60
✓
The toolkit produces a Jira-shaped draft at tickets/draft/<finding-id>.md with: summary, reproduction steps, affected file:line ranges, 3-5 testable acceptance criteria, and an implementation note (a suggestion, not a prescription).
EXAMPLE DRAFT — tickets/draft/...c9e21a60.md
# BIMS-1234 — Login form 500s on empty email

## Summary
POST /users/login with empty email_w returns HTTP 500 instead of
validating to a 200 with a "email required" error. Affects
PropertyOrganizer-Web.

## Reproduction
1. Visit http://staging.propertyorganizer.com/users/login
2. Submit the form with email_w='' and password_w='anything'
3. Observe: HTTP 500 with stack trace
4. Expected: HTTP 200, login form re-rendered with error

## Affected files (cite during fix)
- application/modules/users/controllers/users.php:106
  (form_validation rule allows empty value through)
- application/modules/users/models/users_model.php:347
  (check_front_login doesn't guard against empty email)

## Acceptance criteria
- [ ] AC1: POST /users/login with empty email_w returns HTTP 200
- [ ] AC2: Response body contains "Email is required" error string
- [ ] AC3: No row added to ci_sessions on empty-credential submit
- [ ] AC4: Existing happy-path login (valid creds) continues to work

## Implementation note (suggestion, not prescription)
Add `required` to the form_validation rule at users.php:106.
Confirm xss_clean doesn't already strip the value to empty.

---
Finding: BIMS-F-2026-05-19-c9e21a60
2

Review before posting

Open the draft file and verify:

  • The reproduction steps work when you run them
  • The cited file:line ranges are correct (open the file and look)
  • The acceptance criteria are testable — each one a thing you can verify in 30 seconds
  • The implementation note is a suggestion, not a demand — vendors can fix differently as long as ACs pass
3

Promote to Jira

TYPE INSIDE CLAUDE
> /bims-promote BIMS-F-2026-05-19-c9e21a60

While the Atlassian integration isn't wired yet, this outputs Jira-ready formatted text you can paste manually into the BIMS-* project. The finding's status flips to promoted and the Jira ID gets recorded.

⚠
Always BIMS-*, never PAS-*. The Jira project for tickets you write is BIMS-* (BIMS-Corp's ops space). PAS-* is the subcontractor team's internal working space — you never write tickets there directly. The toolkit will refuse if you try. Add the label ai-drafted when posting so it's clear this came from the workbench.

PART 6

Asking & diagnosing

per question / per finding

Two related workflows. /bims-ask answers a codebase question with citations. /bims-diagnose runs a structured 5-step diagnostic on a finding before you draft the ticket — sharpens the acceptance criteria significantly.

1

Asking a codebase question

When: you need to know how some piece of the system works — what table a model writes to, where a function is called from, what the schema of users is, why a certain redirect happens. Instead of greping for an hour, you ask in plain English and get a cited answer.

TYPE INSIDE CLAUDE
> /bims-ask what database tables does the property creation
   flow write to?

The toolkit consults the code graph (via graphify-bims-* indexers), reads the precise file ranges, and produces an answer with file:line citations for everything it claims. Every claim is verifiable.

2

Questions that work well

  • Specific behavior: "How does the master password backdoor in users_model.php actually work?"
  • Schema: "What columns does the users table have, and what does role_id mean?"
  • Cross-cutting: "Where is STORAGE_AMOUNT_PER_PROPERTY referenced and what does each caller do with it?"
  • Workflow: "What happens after a user submits the property creation form?"
  • Debugging: "Why might POST /users/login return 200 instead of redirecting to /dashboard?"
3

Questions that don't work

  • Yes/no without context: "Is this a good idea?" — the toolkit doesn't have opinions; rephrase as "what are the tradeoffs of X vs Y"
  • Multi-step engineering tasks: "Build me a new login system" — that's a feature request, not a question; open it as a finding instead
  • Out of scope: Questions about iOS/Android repos when only the web graphs are indexed
⚠
Every claim cites. If the toolkit makes a claim without a file:line citation, that claim is unverified and you should distrust it. The contract is: every factual statement is cited. Anything uncited is conjecture — ask for evidence or move on.
4

Diagnosing a finding before ticketing

When: a finding is recorded but it's not yet clear what's actually broken or what the fix should look like. You need to investigate before you draft a ticket.

TYPE INSIDE CLAUDE
> /bims-diagnose BIMS-F-2026-05-19-c9e21a60

The diagnostic protocol does five things:

  1. Reproduce the bug locally (where possible) to confirm it actually exists
  2. Locate the exact code path responsible — file:line for the offending line, not just the controller name
  3. Git contrast the change — is this a longstanding bug, a recent regression, or introduced in a specific commit?
  4. Three hypotheses for what's wrong, each with a falsifiability criterion ("if X is true, we'd see Y in the logs")
  5. Two-track fix proposal — minimum-viable (smallest change that resolves the immediate issue) and ideal (what we'd do with unlimited time)

Output lands at diagnoses/<finding-id>/diagnosis.json. Read it before drafting the ticket — the diagnosis usually sharpens the acceptance criteria significantly.

PART 7

Reviewing a vendor PR

~15 min per PR

When you'd use this: the subcontractor team has submitted a PR fixing one of the tickets you wrote. You need to decide whether it actually fixes the bug — without spending an hour reading the diff. The toolkit produces a per-criterion verdict so your review is structured and defensible.

1

Run the review

TYPE INSIDE CLAUDE
> /bims-review https://github.com/bims-corp-ai/PropertyOrganizer-Web/pull/123

If the Atlassian integration is wired, the toolkit auto-fetches the linked Jira ticket's acceptance criteria. Otherwise, paste them when prompted.

2

Read the per-AC verdict

REVIEW OUTPUT
PR: PropertyOrganizer-Web#123 (BIMS-1234)
Title: Fix login form on empty email
Author: tatva-dev-3

Per acceptance criterion verdict:

AC1: POST /users/login with empty email_w returns HTTP 200
  VERDICT: PASS
  Evidence: application/modules/users/controllers/users.php:108
  The form_validation rule now includes 'required'. Tested via
  curl, empty email returns 200 with error message.

AC2: Response body contains "Email is required" error
  VERDICT: PASS
  Evidence: language/english/users_lang.php:42 ('email-required')
  Validation triggers the lang lookup; literal string is rendered.

AC3: No row added to ci_sessions on empty-credential submit
  VERDICT: LIKELY_PASS
  Evidence: short-circuit at users.php:108 prevents reaching
  set_custom_userdata. Recommend confirming in QA with a manual
  repro rather than purely from diff inspection.

AC4: Existing happy-path login continues to work
  VERDICT: NEEDS_INFO
  Evidence: No automated test covers this. Diff doesn't touch
  the happy path, so likely intact, but verify before merge.

Overall: 2 PASS, 1 LIKELY_PASS, 1 NEEDS_INFO. Recommend
manual verification of AC3 and AC4 before approving.
3

What to do with the verdict

  • All PASS: approve.
  • Any FAIL: request changes — cite the specific AC and evidence.
  • NEEDS_INFO: ask the vendor for the missing evidence (typically a manual repro video or a test case) before approving.
  • LIKELY_PASS: use judgment. Often safe to approve, but if the bug was a regression risk, manually verify.
⚠
Boundary. Under the current operating model the toolkit produces advisory comments only. The subcontractor team currently operates the merge button. Your verdict is a recommendation, not a block. BIMS-Corp owns the merge policy and can change this arrangement at any time — if Greg decides ops should hold the merge button, that's allowed.

PART 8

Daily loop & rules

reference

How a normal ops day fits together, plus the rules that must not be broken. Bookmark this section.

1

The daily loop

  1. Open Terminal, cd ~/Developer/bims-corp-ops
  2. Start session: claude
  3. Always first: please orient
  4. Then one of:
    • Spotted a bug? record a finding: <what you saw>
    • Need to write a ticket? /bims-ticket <finding-id>
    • Need to understand code? /bims-ask <question>
    • Reviewing a vendor PR? /bims-review <PR URL>
2

Health check when something feels off

RUN IN TERMINAL
$ ./bin/doctor

Doctor prints PASS / WARN / FAIL per check. For every FAIL, the remediation command is on the line above. Run that command, then re-run doctor.

3

Rules to never break

  • Never paste literal API keys, passwords, or tokens into any file in this repo — the remote is public.
  • Never write tickets against PAS-* (the subcontractor team's space). Use BIMS-* with the ai-drafted label.
  • Never run git commit --no-verify — the gate is there for a reason. If something's flagged that isn't a real leak, add the fingerprint to .gitleaksignore with a comment.
  • Never edit files under BIMS-Corp-LEGACY/ — legacy is read-only. The harness will refuse, but don't try to work around it.
  • Every claim cites file:line. If you can't cite, you don't actually know — ask the toolkit to find the evidence.
4

What you don't do (under current operating mode)

This handbook is for ops work. There are three things the toolkit can technically do that you, as ops, do not do:

  1. Modify legacy code. Files under BIMS-Corp-LEGACY/ are read-only. The harness refuses writes there, by design. The subcontractor team implements fixes; you write the tickets that describe what needs to happen.
  2. Merge PRs. Under the current operating model, the subcontractor team operates the merge button on legacy repos. Your role is advisory: produce per-AC verdicts that inform the merge decision. BIMS-Corp owns the merge policy and can revise this at any time — that's Greg's call, not yours.
  3. Rotate credentials or remediate leaks directly. If you find a credential leak, file it as a P0 finding and notify Greg. Don't try to rotate keys, revoke tokens, or rewrite git history. The subcontractor team owns the production-side remediation under the current arrangement.
5

When to escalate to Greg

Send to Greg directly (Slack or email) when:

  • A P0 finding is recorded — production-down or active security exposure
  • A credential leak is detected (pre-commit gate fired with a real positive, or you spotted leaked keys in a deployed app)
  • The subcontractor team's PR conflicts with the linked acceptance criteria and they want to merge anyway
  • The toolkit itself is broken (multiple doctor FAILs you can't resolve)
  • You're being asked to do something outside the ops boundary (e.g., write production code, rotate keys)

For everything else — normal bugs, normal tickets, normal PR reviews — use the workflows above. They're designed so escalation is the exception, not the routine.

Severity guide

Default to P2 if you're not sure — over-classifying as P1 dilutes the signal.

SeverityMeaningExamples
P0 Production-down or active security exposure. Drop everything. Login broken in production. Customer data leaking. Credentials committed to public repo.
P1 Critical feature broken or significant risk. Same-week fix. Property creation fails for a subset of users. Auth bypass via known plaintext. Payment processing edge case.
P2 Real bug affecting normal use. Plan into the next sprint. Form validation accepts empty input. Search returns wrong results. Email template renders badly.
P3 Minor / cosmetic / tech-debt. Fix when convenient. Misaligned button. Deprecated function still in use. Inconsistent error message wording.

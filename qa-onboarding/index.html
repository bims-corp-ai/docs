BIMS-Corp · QA Onboarding Guide · Windows 11

You're 60 minutes away from your first bug.

This guide walks you (yes you, the new QA person on a Windows 11 laptop) from no tools installed to finding a real production bug and drafting a complete Jira ticket. Follow it top to bottom. Every command is copy-paste. Every command has an expected-output panel. If something doesn't match, the troubleshooting box right below it tells you what to do.

You will not write code. You will not modify production. Your job is to ask Claude (an AI that already knows all 8 BIMS-Corp codebases) what's broken, confirm it's real, and draft Jira tickets. That's the whole loop.

Part 1: Install →
PART 1

Install WSL2 & Linux tools

~20 min (incl. 1 reboot)

WSL2 ("Windows Subsystem for Linux") is Microsoft's first-party feature that lets you run Linux inside Windows. It's free, built into Windows 11, and is the simplest way to make Windows behave the same as Max's Mac. Every command in this guide runs inside Ubuntu, not PowerShell.

1

Open PowerShell as Administrator

Right-click the Start menu (bottom-left). Click Terminal (Admin) or Windows PowerShell (Admin). A blue window opens. If Windows asks "Do you want to allow this app to make changes?", click Yes.

2

Install WSL2 with one command

Paste this into the PowerShell window and press Enter:

RUN IN POWERSHELL (ADMIN) 
PS C:\> wsl --install
✓
You should see: a list of components downloading (Virtual Machine Platform, Ubuntu, etc.) and a message The requested operation is successful. Changes will not be effective until the system is rebooted.

Run this instead to install Ubuntu specifically:

RUN IN POWERSHELL (ADMIN)
wsl --install -d Ubuntu
wsl --set-default Ubuntu

Your CPU's virtualization extension is turned off in BIOS. Fix:

  1. Reboot. As the laptop powers on, press F2 or Del repeatedly to enter BIOS (the key depends on your laptop brand — Dell is usually F2, Lenovo is F1, HP is F10).
  2. Find a setting called "Intel VT-x", "AMD-V", or "Virtualization Technology". Enable it.
  3. Save (usually F10) and exit. Windows boots normally.
  4. Re-open PowerShell as Admin, re-run wsl --install.

If you don't feel comfortable doing this, ping your IT contact or Max.

3

Reboot your laptop

Save anything you have open in other apps. Restart Windows (Start menu → Power → Restart).

✓
After reboot: Ubuntu opens automatically in a new window and shows Installing, this may take a few minutes.... Wait for it to finish.
4

Create your Ubuntu username + password

When Ubuntu finishes installing, it asks for a UNIX username and password. This is a separate identity from your Windows login — it lives only inside Ubuntu.

  • Username: pick something short and lowercase, e.g. qa or your first name lowercase.
  • Password: pick anything memorable. You don't see characters as you type — that's normal in Linux. Type it twice carefully.
  • Write both down somewhere. You'll need the password when you run sudo commands.
✓
You should see a prompt that looks like qa@laptop-name:~$. That dollar sign means you're at the Ubuntu shell. You're now inside Linux.
5

Install the prerequisite Linux packages

Inside the Ubuntu window, paste this single line and press Enter. It installs everything the BIMS workbench needs (git, jq, sqlite, python, etc.). Type your Ubuntu password when prompted.

RUN IN UBUNTU 
$ sudo apt update && sudo apt install -y \
   git curl unzip jq sqlite3 python3 python3-pip build-essential
✓
You should see a bunch of Setting up <package>... lines, ending with the $ prompt coming back. Takes 2-5 minutes depending on your connection.
6

Install uv (Python package manager)

The BIMS workbench uses uv (a modern Python tool). Two commands:

RUN IN UBUNTU 
$ curl -LsSf https://astral.sh/uv/install.sh | sh
$ source $HOME/.local/bin/env
✓
Verify with uv --version — should print something like uv 0.x.x.
7

Install the GitHub CLI

This lets you authenticate against GitHub from the command line. Paste this whole block:

RUN IN UBUNTU 
$ (type -p wget >/dev/null || sudo apt-get install wget -y) \
   && sudo mkdir -p -m 755 /etc/apt/keyrings \
   && wget -qO- https://cli.github.com/packages/githubcli-archive-keyring.gpg \
      | sudo tee /etc/apt/keyrings/githubcli-archive-keyring.gpg > /dev/null \
   && sudo chmod go+r /etc/apt/keyrings/githubcli-archive-keyring.gpg \
   && echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" \
      | sudo tee /etc/apt/sources.list.d/github-cli.list > /dev/null \
   && sudo apt update && sudo apt install gh -y
✓
Verify with gh --version — should print gh version 2.x.x.
8

Log into GitHub from the command line

This connects your Ubuntu shell to your GitHub account so you can clone the private BIMS-Corp repos.

RUN IN UBUNTU
$ gh auth login

You'll be asked a series of questions. Answer them like this:

  • What account do you want to log into? → GitHub.com
  • What is your preferred protocol? → HTTPS
  • Authenticate Git with your GitHub credentials? → Y (Yes)
  • How would you like to authenticate? → Login with a web browser

It then prints a one-time code (e.g. ABCD-1234) and a URL. Copy the code, press Enter to open the URL in your browser, then paste the code into the GitHub prompt. Approve the login.

✓
Back in the terminal you should see ✓ Logged in as <your-github-username>.

WSL2 + Ubuntu + apt packages + uv + gh + GitHub auth — your Windows is now a Linux dev box.

PART 3

Clone the BIMS-Corp repos

~15 min

Two folders, side by side. The bims-corp-ops workbench is where the AI lives — skills, knowledge graphs, finding database, ticket drafts. The BIMS-Corp-LEGACY/ folder holds the 8 production codebases that you'll be QAing. You read from legacy; you never modify it.

1

Create your working directory

We'll use ~/Developer as the parent folder. ~ means your Ubuntu home folder.

RUN IN UBUNTU
$ mkdir -p ~/Developer
$ cd ~/Developer
2

Clone the workbench

RUN IN UBUNTU
$ git clone https://github.com/bims-corp-ai/bims-corp-ops.git
$ cd bims-corp-ops
✓
You should see Cloning into 'bims-corp-ops'... done. The workbench is ~250 MB.

Your GitHub account isn't in the bims-corp-ai org with access to this repo. Confirm by visiting https://github.com/bims-corp-ai/bims-corp-ops. If you see 404, ping Max with your GitHub username; he'll add you. Then re-run the clone command.

3

Clone all 8 legacy repos in one shot

The workbench has a helper script that clones every BIMS-Corp legacy repo to ~/Developer/BIMS-Corp-LEGACY/ in parallel:

RUN IN UBUNTU (FROM bims-corp-ops/)
$ mkdir -p ~/Developer/BIMS-Corp-LEGACY
$ ./bin/clone-legacy
✓
You should see 8 repos cloning (LinkServicePro-Web, LinkInspectPro-Web, PropertyOrganizer-Web, SuperAdmin-Web, and the 4 mobile ones). Takes 10-15 minutes total — ~1.5 GB of code.

Same fix as step 2 — your GitHub account doesn't have access to that specific repo. Note which repos failed, send the list to Max with your GitHub username, wait for confirmation, then re-run ./bin/clone-legacy (it skips already-cloned repos, only retries missing ones).

Bootstrap the workbench

~10 min

One config file to edit, then one command to wire everything together (Python deps, database, MCP servers, knowledge graphs).

1

Copy the example config to your local config

2

Find your Ubuntu username

You'll need this for the next step:

RUN IN UBUNTU
$ whoami
✓
It prints your Ubuntu username — e.g. qa. Write it down; we use it as <you> in the next step.
3

Edit the config file

Open it in the nano editor (simplest CLI editor on Linux):

RUN IN UBUNTU
$ nano state/local-config.json

Fill in these fields (replace <you> with the Ubuntu username from step 2, and your name where indicated):

state/local-config.jsonedit these fields
# required:
"machine_id":       "<your-firstname>-qa-laptop",
"operator":         "<your-email@bimscorp.com>",
"BIMS_OPS_ROOT":    "/home/<you>/Developer/bims-corp-ops",

PART 5

Your first conversation with Claude

5 min

Now we verify it actually works. You'll ask Claude a real question about LinkServicePro-Web and watch it answer with file:line citations.

1

Open Claude from the workbench directory

The working directory matters — Claude needs to be inside bims-corp-ops so it picks up the skills and MCP config.

RUN IN UBUNTU
$ cd ~/Developer/bims-corp-ops
$ claude
✓
Claude takes a few seconds to load its skills, then shows the input prompt at the bottom of the terminal. You'll see a list of available skills like /bims-ask, /bims-diagnose, /bims-ticket.
2

Start with /bims-orient

This is the "where are we" command. Always run it first in any new Claude session. It prints today's project state in ~3 seconds.

Type this and press Enter:

TYPE INSIDE CLAUDE
> /bims-orient
✓
Claude prints a summary: open findings count by severity (P0/P1/P2/P3), recent decisions, last legacy-repo sync, and a list of "traps" (known constraints to be aware of). Read it briefly. This is your daily compass.
3

Ask a real codebase question

Now we'll do something real. Type:

TYPE INSIDE CLAUDE
> /bims-ask how does invoice payment work in LinkServicePro-Web?

Claude will: query the LSP-Web knowledge graph, identify the relevant files, read the precise line ranges, and answer you with citations. Every claim ends with file:line.

✓
Something like this:
claude · > /bims-ask
CLAUDE
Invoice payment in LinkServicePro-Web works via an emailed link:

1. sendInvoiceToClient() at app/Repositories/InvoiceRepository.php:1442 builds the email body for an invoice.

2. At InvoiceRepository.php:1495, the payment URL is built: route('invoice_payment', ['invoice' => encrypt_decrypt($invoiceData->id)]).

3. The encrypted invoice_id becomes the URL token the customer clicks. The token is decrypted at the payment controller to look up the invoice.
!
The cite-or-it-doesn't-count rule. Every claim Claude makes about code should end with file:line. If it doesn't, push back: "cite that please." If Claude can't, the claim is invented — don't trust it. This is your single most important habit.

Part 6: Hunt a bug →
PART 6

Hunt your first bug, end-to-end

~15 min

Five commands. Real bug. Jira-ready ticket at the end. We'll walk through a real example you can copy beat for beat the first time, then explain how to apply it to bugs you discover yourself.

1

Investigate a suspicion

Real bug-hunting starts with a hunch — a customer complaint, a security worry, a "this code feels old." You don't need to know where in the code to look. Tell Claude the symptom; it finds the location.

For this walkthrough, type:

TYPE INSIDE CLAUDE
> /bims-ask the QA team got a customer complaint that they
   could see someone else's invoice by tweaking the URL. Is
   there anything in LinkServicePro-Web's invoice flow that
   would let that happen?
✓
Claude traces the invoice URL → finds encrypt_decrypt() at GeneralHelper.php:370-386 → reads the implementation → identifies hardcoded AES key + static IV → explains the attack: anyone with repo access can forge any token. All with file:line citations.
2

Record the finding

If Claude found something real, just tell it:

TYPE INSIDE CLAUDE
> record this as a finding
✓
Claude calls mcp__bims-store__record_finding with the right severity rubric and prints a finding ID like BIMS-F-2026-05-27-ddca6b27. Severity is auto-computed from four facts — this one comes out P0 / CRITICAL because it lets attackers forge tokens at production scale with zero defenses.
3

Get a structured diagnosis

For P0 and P1 findings, run /bims-diagnose — it produces 3 competing hypotheses (with falsifiability criteria) plus a two-track fix (minimum-viable + ideal). Substitute the finding ID you just got:

TYPE INSIDE CLAUDE
> /bims-diagnose <your-finding-id>
✓
Claude writes diagnoses/<finding-id>/diagnosis.json with: reproduction, suspect file:line range, contrast (LONGSTANDING / REGRESSION / INTRODUCED_HERE with the commit + author), 3 hypotheses ranked by likelihood, and Track A (minimum-viable fix with diff) + Track B (ideal fix).
4

Draft a Jira ticket

TYPE INSIDE CLAUDE
> /bims-ticket <your-finding-id>
✓
Claude writes tickets/draft/<finding-id>.md — a complete Jira-shaped ticket with: title, severity, repo, labels, "Why this matters" (plain-English impact), current/expected behavior, root cause, two authorized tracks (A and B), and a full Implementation Note (files to touch, patterns to follow, patterns to avoid, test to write, definition of done, complexity tier).

Open the draft to review it. In a new Ubuntu window (right-click the Ubuntu icon → "New window"):

RUN IN UBUNTU (second window)
$ cd ~/Developer/bims-corp-ops
$ less tickets/draft/*.md
# press q to exit less
i
If the draft is wrong — Claude misunderstood the impact, suggested the wrong files, etc. — just tell Claude in the chat: "the Implementation Note has the wrong entry point — it's StripeController.php not InvoiceController.php. update the draft." Claude rewrites the file. Iterate until you're happy.
5

Promote to Jira

TYPE INSIDE CLAUDE
> /bims-promote <your-finding-id>

Right now (until the Jira API token is wired), Claude prints a copy-paste block:

expected output
==== COPY THIS INTO JIRA ====
Project: BIMS
Issue type: Bug
Summary: [Security/Crypto] encrypt_decrypt() helper uses hardcoded AES key...
Labels: ai-drafted, security, crypto, complexity-M

Description:
---
<full ticket body>
---

Now: open Jira in your browser, click Create Issue, paste the Summary into the summary field, paste the Description into the description field, add the labels exactly as listed, and submit. Copy the resulting BIMS-NNNN issue ID.

Back in Claude, record the Jira ID:

TYPE INSIDE CLAUDE
> the jira id for that ticket is BIMS-5402
✓
Claude updates the finding to mark it as promoted with the Jira ID attached, so the audit trail is complete.
i
Once the Jira API is wired (Max is working on it), /bims-promote will create the issue automatically — no manual paste. You won't have to change your workflow when that lands; it just gets faster.
Part 6 complete
You ran the full bug-hunt loop end-to-end. Future bugs follow the exact same 5 commands.
Part 7: Daily workflow →
PART 7

Your daily workflow

reference

How a normal QA day fits together. Don't memorize — just keep this guide bookmarked. The same 5 commands cover 95% of what you'll do.

1

Start of day (3 commands)

EVERY MORNING
$ cd ~/Developer/bims-corp-ops
$ git pull origin main      # pulls latest skills + graphs from Max
$ claude                    # opens Claude

> /bims-orient              # prints today's project state
2

Throughout the day (per bug)

Each bug = the same 5 commands from Part 6:

  1. /bims-ask <the question or area you're investigating>
  2. If real: record this as a finding
  3. For P0 / P1: /bims-diagnose <finding-id>
  4. /bims-ticket <finding-id>
  5. /bims-promote <finding-id> → paste into Jira → tell Claude the BIMS-NNNN
3

Mid-day check-in

Talk to Claude in plain English. Examples:

USEFUL QUERIES
> show me my findings from today
> which P0 and P1 findings are still open across all repos?
> what bugs has TatvaSoft closed in the last 7 days?
> remind me where I left off yesterday
4

End of day — share your draft tickets with Max

While each person has a local findings database (day 1), Max can't see your draft tickets unless you push them. Run this at the end of each working day:

RUN IN UBUNTU
$ cd ~/Developer/bims-corp-ops
$ git checkout -b qa/$(date +%Y%m%d)-<yourname>-tickets
$ git add tickets/draft/
$ git commit -m "QA tickets drafted $(date +%Y-%m-%d)"
$ git push -u origin qa/$(date +%Y%m%d)-<yourname>-tickets
$ gh pr create --base main --title "QA tickets $(date +%Y-%m-%d)"

Ping Max in Slack with the PR link. He'll review + merge so the tickets are visible to everyone.

i
Future state: once Max migrates the team to shared Turso, your findings appear in his /bims-orient automatically — no daily PR needed. You won't change your workflow when that lands.
5

Stopping mid-task

Just exit Claude (Ctrl+D or type /exit). Your findings + tickets are saved to disk. Tomorrow:

NEXT MORNING
$ cd ~/Developer/bims-corp-ops
$ claude
> /bims-orient
> remind me where I left off — which finding was I working on?

Claude reads the audit log and brings you back up to speed.

5-minute glossary

advisory-tier — current operating mode where AI finds bugs and drafts tickets but never modifies code. Your mode.
workbench-tier — Max's mode; the AI can write code under guardrails. Not relevant to you.
finding — an entry in the bugs database. One row per bug. ID like BIMS-F-YYYY-MM-DD-XXXXXX.
diagnosis — structured analysis: 3 hypotheses + 2 fix tracks. Lives at diagnoses/<id>/diagnosis.json.
Implementation Note — the section of a ticket that tells TatvaSoft exactly what files to touch and what tests to write. Required for promotion.
trap — a known constraint about the codebase (e.g. "CI 2.1.4 doesn't support PHP 8.1 idioms"). Surfaced by /bims-orient.
graphify — the system that builds knowledge graphs of each codebase. One MCP per repo. Claude uses these to navigate.
MCP — Model Context Protocol; how Claude talks to specialized servers. You don't talk to MCPs directly.
severity rubric — deterministic algorithm that converts 4 facts about a finding into P0/P1/P2/P3.
TatvaSoft — the subcontractor team that writes the actual fixes. Your tickets go to them via Jira.

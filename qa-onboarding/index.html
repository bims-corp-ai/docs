Part 1: Install →
PART 1

Install WSL2 & Linux tools

~20 min (incl. 1 reboot)

WSL2 ("Windows Subsystem for Linux") is Microsoft's first-party feature that runs Linux inside Windows. Free, built into Windows 11. The workbench is Linux-native, so everything from here runs inside Ubuntu, not PowerShell.

1

Open PowerShell as Administrator

Right-click the Start menu. Click Terminal (Admin) or Windows PowerShell (Admin). A blue window opens. If Windows asks "Do you want to allow this app to make changes?", click Yes.

2

Install WSL2 with one command

Paste this into the PowerShell window and press Enter:

RUN IN POWERSHELL (ADMIN) 
PS C:\> wsl --install
✓
You should see: a list of components downloading (Virtual Machine Platform, Ubuntu, etc.) and a message The requested operation is successful. Changes will not be effective until the system is rebooted.

Run this instead to install Ubuntu specifically:

RUN IN POWERSHELL (ADMIN)
wsl --install -d Ubuntu
wsl --set-default Ubuntu

Your CPU's virtualization extension is off in BIOS. This is a one-time toggle.

  1. Reboot. As the PC powers on, press F2 or Del repeatedly to enter BIOS. The key depends on the motherboard — most desktop BIOSes flash the right key on the boot screen for a second.
  2. Find a setting called "Intel VT-x", "AMD-V", or "Virtualization Technology". Enable it.
  3. Save (usually F10) and exit. Windows boots normally.
  4. Re-open PowerShell as Admin and re-run wsl --install.

If the PC's BIOS is locked or the setting isn't visible, raise it in tomorrow's session — Max has the IT context for each machine and can walk through it with whoever owns the hardware.

3

Reboot

Save anything you have open in other apps. Restart Windows (Start menu → Power → Restart).

✓
After reboot: Ubuntu opens automatically in a new window and shows Installing, this may take a few minutes.... Wait for it to finish.
4

Create your Ubuntu username + password

When Ubuntu finishes installing, it asks for a UNIX username and password. This is a separate identity from your Windows login — it lives only inside Ubuntu.

  • Username: short, lowercase, no spaces. Your first name lowercase works fine (niam, jose, sal).
  • Password: anything memorable. You don't see characters as you type — that's normal in Linux. Type it twice carefully.
  • Write both down. You'll need the password whenever you run sudo.
✓
You should see a prompt like niam@desktop:~$. The dollar sign means you're at the Ubuntu shell — you're inside Linux now.
5

Install the prerequisite Linux packages

Inside the Ubuntu window, paste this single line and press Enter. It installs git, jq, sqlite, python, and the build tools the workbench needs. Type your Ubuntu password when prompted.

RUN IN UBUNTU 
$ sudo apt update && sudo apt install -y \
   git curl unzip jq sqlite3 python3 python3-pip build-essential
✓
You should see a bunch of Setting up <package>... lines, ending with the $ prompt coming back. 2–5 minutes depending on connection.
6

Install uv (Python package manager)

The workbench uses uv (a modern Python tool). Two commands:

RUN IN UBUNTU 
$ curl -LsSf https://astral.sh/uv/install.sh | sh
$ source $HOME/.local/bin/env
✓
Verify with uv --version — should print uv 0.x.x.
7

Install the GitHub CLI

This lets you authenticate against GitHub from the command line. Paste the whole block:

RUN IN UBUNTU 
$ (type -p wget >/dev/null || sudo apt-get install wget -y) \
   && sudo mkdir -p -m 755 /etc/apt/keyrings \
   && wget -qO- https://cli.github.com/packages/githubcli-archive-keyring.gpg \
      | sudo tee /etc/apt/keyrings/githubcli-archive-keyring.gpg > /dev/null \
   && sudo chmod go+r /etc/apt/keyrings/githubcli-archive-keyring.gpg \
   && echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" \
      | sudo tee /etc/apt/sources.list.d/github-cli.list > /dev/null \
   && sudo apt update && sudo apt install gh -y
✓
Verify with gh --version — should print gh version 2.x.x.
8

Log into GitHub from the command line

This connects your Ubuntu shell to your GitHub account so you can clone the private BIMS-Corp repos.

RUN IN UBUNTU
$ gh auth login

Answer the prompts like this:

  • What account do you want to log into? → GitHub.com
  • What is your preferred protocol? → HTTPS
  • Authenticate Git with your GitHub credentials? → Y (Yes)
  • How would you like to authenticate? → Login with a web browser

It prints a one-time code (e.g. ABCD-1234) and a URL. Copy the code, press Enter to open the URL in your browser, then paste the code into the GitHub prompt. Approve the login.

✓
Back in the terminal you'll see ✓ Logged in as <your-github-username>.

PART 3

Clone the BIMS-Corp repos

~15 min

Two folders, side by side. bims-corp-ops is the workbench — where the AI lives (skills, knowledge graphs, finding database, ticket drafts). BIMS-Corp-LEGACY/ holds the 8 production codebases you're QAing against. You read from legacy; you never modify it (the workbench enforces this).

1

Create your working directory

We use ~/Developer as the parent folder. ~ means your Ubuntu home folder.

RUN IN UBUNTU
$ mkdir -p ~/Developer
$ cd ~/Developer
2

Clone the workbench

RUN IN UBUNTU
$ git clone https://github.com/bims-corp-ai/bims-corp-ops.git
$ cd bims-corp-ops
✓
You should see Cloning into 'bims-corp-ops'... done. The workbench is ~250 MB.

Your GitHub account isn't in the bims-corp-ai org yet. Confirm by visiting github.com/bims-corp-ai/bims-corp-ops. If you see a 404, tell Max your GitHub username in the session — he'll add you and you re-run the clone.

3

Clone all 8 legacy repos in one shot

The workbench has a helper script that clones every BIMS-Corp legacy repo to ~/Developer/BIMS-Corp-LEGACY/. It's idempotent — re-running skips repos that already exist.

RUN IN UBUNTU (FROM bims-corp-ops/)
$ mkdir -p ~/Developer/BIMS-Corp-LEGACY
$ ./bin/clone-legacy
✓
You should see 8 repos cloning in sequence (LinkServicePro-Web, LinkInspectPro-Web, PropertyOrganizer-Web, SuperAdmin-Web, and the 4 mobile ones), ending with clone-legacy: cloned=8 skipped=0 failed=0. 10–15 minutes total; ~1.5 GB of code.

Your GitHub account doesn't have access to that specific legacy repo yet. The summary line at the end tells you which failed. Send Max the failed-repo names in the session; once he adds you, re-run ./bin/clone-legacy — it skips the ones already on disk and retries the missing ones.

PART 4

Bootstrap the workbench

~10 min

One config file to fill in, then one command to wire everything together (Python deps, database, MCP servers, knowledge graphs).

1

Copy the example config to your local config

RUN IN UBUNTU (FROM bims-corp-ops/)
$ cp etc/local-config.example.json state/local-config.json
2

Find your Ubuntu username

You'll need this for the next step:

RUN IN UBUNTU
$ whoami
✓
It prints your Ubuntu username — e.g. niam. Use this as <you> in the next step.
3

Edit the config file

Open it in nano (simplest CLI editor on Linux):

RUN IN UBUNTU
$ nano state/local-config.json

Set these fields (replace <you> with the Ubuntu username from step 2, and pick a machine_id that identifies you and the machine):

state/local-config.jsonedit these fields
# required:
"machine_id":       "<firstname>-bimscorp-desktop",
"operator":         "<your work email>",
"BIMS_OPS_ROOT":    "/home/<you>/Developer/bims-corp-ops",
"BIMS_LEGACY_ROOT": "/home/<you>/Developer/BIMS-Corp-LEGACY",
"mode":             "secondary",
"sync_enabled":     false

# add this line (a local sqlite store for day 1):
"BIMS_STORE_URL":   "file:///home/<you>/Developer/bims-corp-ops/state/bims-store.db"

# delete these two lines (they're for the shared Turso store, which we'll wire up later):
"BIMS_STORE_URL_BASE":  "..."
"BIMS_STORE_TOKEN_FILE": "..."

Save and exit nano: Ctrl+O, Enter to confirm filename, Ctrl+X to exit.

i
Why local sqlite instead of shared Turso? Day 1, each of you gets your own local findings database — simpler to bootstrap. Once we're all running comfortably, we migrate the team to shared Turso so everyone sees each other's findings in the same orient call.
4

Run the bootstrap script

One command runs all 11 setup steps. You don't need to know what each one does — just watch for unexpected FAILs.

RUN IN UBUNTU (FROM bims-corp-ops/)
$ ./bin/setup --mode secondary --no-launchd --skip-indexes
✓
You should see 11 numbered steps:
expected output

  2/11 uv sync ......................... OK
  3/11 state/local-config.json ......... OK
  4/11 clone legacy repos .............. OK
  5/11 render config files ............. OK
  6/11 migrate db ...................... OK
  7/11 graphify indexes ................ SKIPPED
  8/11 launchd ......................... SKIPPED

Summary: 68 pass / 1 warn / 7 fail
(the 7 FAILs are EXPECTED — they're placeholder

Don't try to fix it yourself the first time. Copy the full output (especially the FAIL lines) and send it to Max with:

  1. Which step number failed (e.g. "step 6 / migrate db")
  2. The full error text below that step
  3. Output of cat state/local-config.json so Max can verify your paths

The 7 expected FAILs are 4 no_driver_resolved + 3 harness_unbootstrapped — placeholders. If you see additional FAILs you don't recognize, run:

RUN IN UBUNTU

Send the full output to Max.

Sanity-check the connection

Type this into Claude and press Enter:

TYPE INSIDE CLAUDE

✓
Claude explains the BIMS-Corp workbench, names the 8 repos it has indexed, and lists the skills available to you (/bims-ask, /bims-diagnose, /bims-ticket, /bims-promote, etc.). Read the reply — it confirms everything's wired correctly.

Ask a real codebase question

Now something real. Type:

TYPE INSIDE CLAUDE
> /bims-ask how does invoice payment work in LinkServicePro-Web?

Claude queries the LSP-Web knowledge graph, identifies the relevant files, reads the precise line ranges, and answers with citations. Every claim ends with a file:line reference.

✓
Something like this:
claude · > /bims-ask
CLAUDE
Invoice payment in LinkServicePro-Web works via an emailed link:

1. sendInvoiceToClient() at app/Repositories/InvoiceRepository.php:1442 builds the email body for an invoice.

2. The payment URL is constructed inside that method via Laravel's route() helper, with the invoice ID encoded by a helper from app/Helpers/Global/GeneralHelper.php.

3. The encoded invoice ID becomes the URL token the customer clicks. The token is decoded at the payment controller to look up the invoice.
!
The cite-or-it-doesn't-count rule. Every claim Claude makes about code should end with file:line. If it doesn't, push back: "cite that please." If Claude can't cite, the claim is invented — don't trust it. This is your single most important habit.

Part 6: Hunt a bug →
PART 6

Hunt your first bug, end-to-end

~15 min

Five commands. Real bug. Jira-ready ticket at the end. We walk through it once together in the session — after that, the same five commands handle every bug you find.

1

Investigate a suspicion

Bug-hunting starts with a hunch — a customer complaint, a behavior that feels wrong, a "this code looks old." You don't need to know where in the code to look. Tell Claude the symptom; it finds the location.

For this walkthrough, type:

TYPE INSIDE CLAUDE
> /bims-ask a customer says they could see someone else's
   invoice by tweaking the URL. Is there anything in
   LinkServicePro-Web's invoice flow that would let that
   happen?
✓
Claude traces the invoice URL flow, reads the relevant helper that signs the URLs, identifies the specific weakness, and explains the attack — all with file:line citations you can verify.
2

Record the finding

If Claude found something real, just tell it:

TYPE INSIDE CLAUDE
> record this as a finding
✓
Claude writes the finding to the workbench's findings database and prints a finding ID like BIMS-F-2026-05-27-ddca6b27. Severity is auto-computed from four facts (impact, likelihood, population affected, defenses remaining) and printed alongside the ID — e.g. P0 / CRITICAL.
3

Get a structured diagnosis

For P0 and P1 findings, run /bims-diagnose — it produces 3 competing hypotheses (with falsifiability criteria) plus a two-track fix (minimum-viable and ideal). Substitute the finding ID you just got:

TYPE INSIDE CLAUDE
> /bims-diagnose <your-finding-id>
✓
Claude writes diagnoses/<finding-id>/diagnosis.json with: reproduction, suspect file:line range, git-contrast (LONGSTANDING / REGRESSION / INTRODUCED_HERE with the commit + author), 3 hypotheses ranked by likelihood, and Track A (minimum-viable fix) + Track B (ideal fix).
4

Draft a Jira ticket

TYPE INSIDE CLAUDE
> /bims-ticket <your-finding-id>
✓
Claude writes tickets/draft/<finding-id>.md — a complete Jira-shaped ticket: title, severity, repo, labels, "Why this matters" (plain-English impact), current/expected behavior, root cause, two authorized fix tracks (A and B), and a full Implementation Note (files to touch, patterns to follow, patterns to avoid, test to write, definition of done, complexity tier).

Open the draft to review it. In a new Ubuntu window (right-click the Ubuntu icon → "New window"):

RUN IN UBUNTU (second window)
$ cd ~/Developer/bims-corp-ops
$ less tickets/draft/*.md
# press q to exit less
i
If the draft is wrong — Claude misunderstood the impact, named the wrong file, etc. — just tell Claude in the chat: "the Implementation Note has the wrong entry point — it's StripeController.php not InvoiceController.php. update the draft." Claude rewrites the file. Iterate until you're happy.
5

Promote to Jira

TYPE INSIDE CLAUDE
> /bims-promote <your-finding-id>

Until the Jira API is wired (in progress), Claude prints a copy-paste block:

expected output
==== COPY THIS INTO JIRA ====
Project: BIMS
Issue type: Bug
Summary: [Security] LinkServicePro-Web invoice URL signing is forgeable...
Labels: ai-drafted, security, complexity-M

Description:
---
<full ticket body>
---

Open Jira in your browser, click Create Issue, paste the Summary into the summary field, paste the Description into the description field, add the labels exactly as listed, and submit. Copy the resulting BIMS-NNNN issue ID.

Back in Claude, record the Jira ID:

TYPE INSIDE CLAUDE
> the jira id for that ticket is BIMS-5402
✓
Claude updates the finding to mark it as promoted with the Jira ID attached, closing the audit trail.
i
Once the Jira API is wired, /bims-promote creates the issue automatically — no manual paste. The five-command flow doesn't change; it just gets faster.
Part 6 complete
You ran the full bug-hunt loop end-to-end. Future bugs follow the same five commands.

PART 7

Role variants — how Niam, Jose, and Sal each use this

reference

The five-command loop in Part 6 is the core — everyone uses it. But each of you comes at the BIMS-Corp codebases from a different angle. This section shows how the same tool serves three different jobs.

Niam Head of IT · BIMS-Corp PM

Your lens: portfolio view — what's open, what's aging, what TatvaSoft has in flight.

You'll use /bims-ask less for "find me a bug" and more for "give me the state of the work." Useful queries:

QUERIES NIAM RUNS
> show me all open P0 and P1 findings across the 8 repos
> which findings have been open longest without a Jira ID?
> summarize this week's findings by repo and severity
> which findings touch the invoice flow in LSP-Web?
> what tickets did Jose draft yesterday?

You'll also be the one routing tickets to TatvaSoft once they're in Jira, and the one checking that fix PRs match the Implementation Note in the ticket. Part 6 still applies when YOU find a bug — but the day-to-day will lean on these triage queries.

Jose QA

Your lens: bug hunter. Part 6 IS your loop.

Every bug report or QA scan goes through the same five commands. Your job is to keep a high bar on what becomes a finding — false-positive findings waste TatvaSoft's time, so if Claude reports something and you're not convinced, push back:

QA-FLAVORED PROBES
> cite that — what file:line are you reading from?
> reproduce this against the current main branch
> what would falsify this hypothesis?
> what's the population of users actually affected here?

If Claude's severity feels off, challenge it on the specific input ("worst_case isn't silent-degrade, it's integrity-bypass — re-rate it") and it will re-compute. If you and Claude still disagree, the call is Max's.

Sal Real-user QA · GC Environmental

Your lens: production user. The most valuable signal in the whole team.

You use LinkServicePro / LinkInspectPro / PropertyOrganizer every day to do actual work for GC Environmental. That means your bug reports start from "I just clicked X and Y happened" — and that's where the high-value findings come from. Code-only review can't see those.

Your version of the Part 6 loop starts from the symptom, not the codebase:

HOW SAL STARTS A BUG REPORT
> /bims-ask in LinkServicePro just now I tried to upload a
   work-order photo and the page froze. Walk through the
   upload flow and tell me where it could have hung.

> /bims-ask in PropertyOrganizer, when I edit a contact
   and save, it sometimes shows the OLD address back. What
   in the save flow could explain that?

> /bims-ask on LSP invoices, the payment link in my email
   sent the customer to a DIFFERENT invoice than the one I
   sent. How is that possible — what builds that URL?

From there, it's the same five commands as Jose. The difference is that your starting prompt is grounded in a real user action with a real timestamp — which makes the finding stronger when it lands in front of TatvaSoft.

i
Privacy note: when you describe a user action to Claude, don't paste customer PII (real customer names, addresses, invoice IDs from production). Refer to "the customer" or "that invoice" — Claude doesn't need the literal value to trace the code path, and the workbench remote is public.

Your daily workflow

How a normal day fits together. Don't memorize — keep this page bookmarked. The same five commands cover 95% of what you'll do.

Plain English. Examples:

USEFUL QUERIES
> show me my findings from today
> which P0 and P1 findings are still open across all repos?
> what did I work on yesterday?
> which findings touch the property-edit flow?
4

End of day — share your draft tickets

While each of you has a local findings database (day 1), Max can't see your drafts until you push them. Once a day — when you've got something worth sharing — run this:

RUN IN UBUNTU
$ cd ~/Developer/bims-corp-ops
$ git checkout -b qa/$(date +%Y%m%d)-<yourname>-tickets
$ git add tickets/draft/
$ git commit -m "tickets drafted $(date +%Y-%m-%d)"
$ git push -u origin qa/$(date +%Y%m%d)-<yourname>-tickets
$ gh pr create --base main --title "tickets $(date +%Y-%m-%d)"

Send Max the PR link. He reviews and merges so the tickets are visible to everyone.

i
Future state: once the team is on the shared Turso store, your findings appear in everyone's startup orient automatically — no daily PR needed. Workflow doesn't change; the manual sharing step just goes away.
5

Stopping mid-task

Just exit Claude (Ctrl+D or type /exit). Findings + ticket drafts are saved to disk. Next time you start Claude:

NEXT SESSION
$ cd ~/Developer/bims-corp-ops
$ claude
> what was I working on last? bring me back up to speed.

Claude reads the audit log and the open-finding list and tells you where to pick up.

5-minute glossary

advisory-tier — the current mode where AI finds bugs and drafts tickets but doesn't modify production code. Your mode.
workbench-tier — Max's mode; AI can write code under engineering guardrails. Not relevant to you.
finding — an entry in the bugs database. One row per bug. ID like BIMS-F-YYYY-MM-DD-XXXXXX.
diagnosis — structured analysis: 3 hypotheses + 2 fix tracks. Lives at diagnoses/<id>/diagnosis.json.
Implementation Note — the section of a ticket that tells TatvaSoft exactly what files to touch and what tests to write. Required for promotion.
trap — a known constraint about the codebase (e.g. "CI 2.1.4 doesn't support PHP 8.1 idioms"). Surfaced on Claude startup.
graphify — the system that builds knowledge graphs of each codebase. One MCP per repo. Claude uses these to navigate.
MCP — Model Context Protocol; how Claude talks to specialized servers. You don't talk to MCPs directly.
severity rubric — the deterministic algorithm that converts 4 facts about a finding into P0/P1/P2/P3.
BIMS-Corp — Building Information Management Systems Corporation, the legal owner of the 8 codebases. Greg Collins is CEO.
TatvaSoft / Codepaper — the subcontractor teams that write the actual fixes in the legacy repos. Your tickets reach them via Jira.
